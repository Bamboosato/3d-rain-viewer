## 1. 依頼事項と作業範囲

本書に従い、コード修正、回帰テスト、自動ブラウザテスト、結果報告まで実施する。実機確認は依頼者が別途実施するため、開発者の作業項目・完了条件には含めない。実機確認待ちを理由に、本書の実装・自動テストを未完了にしない。

着手時に対象リポジトリの最新ブランチ、作業ツリー、AGENTS.mdを確認し、レビュー基準との差分を把握する。既に修正済みの項目は根拠を示して既存修正を利用する。行番号はレビュー時点の目安であり、関数と処理経路で該当箇所を特定する。

現在の作業ディレクトリが別プロジェクトの場合は、そのプロジェクトを変更しない。対象リポジトリ用の作業場所で作業する。

対象は以下とする。

- 背景地図・AW3D標高タイルの取得、メモリキャッシュ、OPFS、代替Cache Storage。
- 気象庁ナウキャスト・予測とJAXA GSMaPのカタログ、フレーム取得、再試行、表示更新。
- Service Workerの更新、キャッシュ削除、オフライン復元。
- お気に入りの保存、読み出し、JSON／同期URLの取り込み、取り消し。
- 上記に必要なエラー表示、最小限の診断情報、自動テスト。

新機能追加、地図描画基盤の全面変更、本番公開、マージは本書の対象外とする。依存関係の追加は必要最小限とし、選定理由を記録する。

## 2. 根拠と最優先で防ぐ不具合

前回レビューはコード読解と、対象関数・ブラウザAPIモックを用いた17シナリオの確認に基づく。レビュー用の一時的な確認コードは、リポジトリの既存回帰テストとは別物である。本修正では継続実行できるテストとして整備する。

優先して防ぐのは次の不具合である。

1. 取得失敗・欠測を「降水なし」と表示する。
2. お気に入りが保存されていないのに保存・取り込み成功と表示する。
3. 選択時刻・ソースと、雨雲画像・地点値が食い違う。
4. 更新時に有効な代替キャッシュや取り込み待ちデータを失う。
5. 一度の通信・ストレージ障害から回復できない。
6. 不要な取得・無制限の保存・過剰な先読みによって負荷を増やす。

コード上の欠陥と、特定端末で実際に発生した原因は区別する。特にOPFS操作の停止、保存処理中断、メモリ圧迫によるページ終了について、今回のレビューだけで原因を断定しない。

## 3. 実装上の共通方針

### 3.1 キャッシュの責任を分ける

| データ | 管理する箇所 | 方針 |
|---|---|---|
| HTML・JS・CSS・アイコン | Service Worker | アプリ本体の世代管理とオフライン起動 |
| 背景地図・変換後の標高タイル | アプリのTileCache層 | メモリ＋永続ストレージ、期限・容量・更新世代を一元管理 |
| JMA時刻一覧・生画像タイル | 気象取得層／SWの専用経路 | カタログは鮮度管理、画像は時刻を含むキーで管理 |
| 合成済み雨雲フレーム | アプリのFrameCache層 | 表示用メモリキャッシュ、バイト上限付き |
| お気に入り・Undo | 専用ストレージ層 | 永続保存結果を呼び出し元へ伝達し、更新の整合性を保証 |

背景地図タイルをTileCacheとSWの両方で独立に再検証・保存する現在の重複は解消する。推奨は、TileCacheが所有する背景タイルの外部リクエストをSWで透過させる構成。気象タイル等、SWで保存を続ける経路はFIX-07・09を満たす。

すべてをOPFSへ移すなどの全面統一は不要。保存方式の能力判定はAPIの存在と実際の操作結果で行い、UA文字列だけで決めない。

### 3.2 失敗を型と状態で扱う

少なくとも以下を区別する。

- データ状態: 正常／部分欠落／取得失敗／期限切れの保存データ。
- 保存状態: 保存完了／保存中／メモリのみ／保存失敗。
- 要求状態: 実行中／成功／失敗／キャンセル／タイムアウト。

エラー情報には処理段階と分類を持たせる。例: network、http、decode、invalid-data、storage-unavailable、quota、timeout、cancelled。UIに内部例外や長いURLをそのまま表示しない。

`Promise.race()`で待機を打ち切るだけでは、元の処理は停止しない。打ち切り後の書き込み・画面更新・キャッシュ世代更新を防ぐ仕組みも実装する。

### 3.3 世代とキーを明確にする

- 気象フレームは配列indexをキャッシュキーにしない。
- JMAはsource、dataset、basetime、validtime、合成形式versionをキーに含める。
- GSMaPはcollection、観測日時、対象範囲、解像度、形式version等を含める。
- 地形キーはcollection／変換方式version、tileSize、z/x/yを含める。
- 要求世代とキャッシュ形式versionを混同しない。
- 現行のArrayBuffer複製を維持し、MapLibreへの転送でキャッシュ本体がdetachされないようにする。

## 4. 個別修正指示

### FIX-01: SWによる代替キャッシュ削除を止める

対象: `public/sw.js` activate処理。

- 現在の2種類以外を全削除する条件を廃止する。
- 削除可能な名前空間と旧世代を明示し、所有していないキャッシュは触らない。
- `rain3d-opfs-fallback-v1`等の有効なデータは保持する。
- キャッシュ形式を変更する場合は、互換読み出しまたは段階移行を実装する。
- 移行の成功確認前に、移行元を削除しない。

完了条件: SWの初回有効化・更新で、有効な代替タイルと他用途のキャッシュが残る。削除すべき旧shell/runtimeだけが整理される。

### FIX-02: 欠測と降水量0を分離する

対象: `src/lib/jmaNowcastClient.ts`、`src/lib/jaxaClient.ts`、`src/App.tsx`、`src/components/Inspector.tsx`等。

- タイル取得結果を成功・失敗・データ提供なし等に分けて返す。通信失敗や404を無条件に無降水と見なさない。
- 提供元が正当な「データなし」を表す仕様は、根拠を確認して明示的に扱う。
- 有効性マスクまたは欠測値を導入し、0mm/hと区別する。
- 全タイル失敗はエラー。部分欠落は欠落範囲と件数を保持する。
- 正常に取得・解釈できた無降水画像は0mm/hとして扱う。
- 統計から欠測を除外する。3×3近傍の取得でも、全近傍欠測なら0にしない。
- `ctx === null`、画像デコード失敗、未対応画像形式を正常フレームにしない。
- 部分結果を保存する場合は、完全な結果と区別し、不足部分を再取得できるようにする。
- 全件失敗したフレームを正常キャッシュへ登録しない。
- `precipitation ?? 0`等、欠測をゼロへ変換する経路を修正する。
- UIは「取得できません」「一部取得できません」「保存済みデータ」等を表示する。旧画像を残す場合は旧画像の時刻を表示する。

完了条件: 全20タイル失敗時に「降水なし」が出ない。部分欠落でも有効領域の値は利用でき、欠落領域は欠測になる。

### FIX-03: お気に入りを永続化できた場合だけ成功扱いにする

対象: `src/lib/favoritesStorage.ts`、Appの保存・削除・取り込み処理、`FavoritesSyncDialog.tsx`。

- 保存APIを非同期の成功／失敗が明確な契約へ変更する。
- 保存成功後に確定した一覧・完了表示を更新する。未保存の入力は保持し、再試行やJSON書き出しで救済する。
- 保存失敗時に「取り込み完了」「保存完了」と表示しない。
- 置き換え取り込みでは、取り込み前のUndoと取り込み後一覧を原子的に確定する。
- 推奨はIndexedDBの同一トランザクションでcurrentとundoを更新する実装。既存localStorageを維持する場合は、一覧とUndoを1レコードにまとめる等、同等の原子性を証明できる方式とする。
- 通常の追加・更新・削除と取り込みを直列化し、古いスナップショットによる上書きを防ぐ。
- Reactのstate updater内に保存副作用を置かない。
- Undoの復元に失敗した場合はUndoを消さない。
- ダウンロード開始は保存完了の検出ではない。「ダウンロードを開始しました」等の正確な文言とし、バックアップ日時も「書き出し操作日時」として意味を明確にする。

移行条件: IndexedDB等へ変更する場合、旧localStorageを検証して読み込み、保存トランザクションが完了した後に移行済みとする。移行に失敗しても旧データを残し、空配列で上書きしない。最終バックアップ日時等、既存メタデータの扱いも記録する。

完了条件: 容量不足・アクセス拒否・トランザクション失敗時に旧保存データが維持され、画面が未保存を通知する。

### FIX-04: 失敗したPromiseを再利用しない

対象: `App.tsx` loadFrameAtIndex、`jaxaClient.ts` getGSMaPImageCollection、および類似のPromiseキャッシュ。

- in-flight登録解除は成功・失敗・キャンセルのすべてで実行する。
- 登録中のPromiseと完了したPromiseの同一性を確認し、新しい処理を誤って削除しない。
- 初期化失敗時はシングルトンPromiseを破棄し、次の要求で初期化可能にする。
- 同一キーの同時要求は引き続き統合する。
- 再試行回数を制限し、永続的な入力不正やキャンセルを無限再試行しない。
- HTTP 429等はRetry-Afterを尊重し、指数バックオフ等で負荷を抑える。

完了条件: 初回失敗→通信回復→再要求で取得関数が再実行され、成功する。同時要求では不要な重複取得が起こらない。

### FIX-05: 最新の表示要求だけを採用する

対象: `App.tsx` loadFrameAtIndex／handleSelectTimeIndex／ソース切り替え、`jaxaClient.ts`のインスペクター状態。

- 取得関数はデータを返す責任に限定し、取得途中でアクティブなインスペクターを変更しない。
- 表示要求ごとに世代番号等を割り当てる。
- 現在のソース・フレームキー・世代が一致した結果だけを画面へ採用する。
- 画像、表示時刻、地点値、ローディング、エラーを同じ採用結果にそろえる。
- 旧要求のfinallyで最新要求のローディングを解除しない。
- 遅延結果をキャッシュへ入れる場合も、そのデータ自身の正しいキーを使う。
- MapViewerの準備完了前に雨雲結果が届いても、準備完了時に最新結果を適用する。ref更新だけに依存して適用機会を失わない。
- 古いloadイベントハンドラーや非同期Inspector生成が、後から新しい表示を上書きしないようにする。

完了条件: A→Bの順で選択しB→Aの順で応答しても、画像・値・時刻はBを維持する。ソース切り替えにも同じ保証がある。

### FIX-06: SW更新と同期URL取り込みを両立させる

対象: `src/main.tsx`、`favoritesTransfer.ts` takeFavoritesPayloadFromLocation、Appの取り込み起動処理。

- 初回のService Worker制御開始を理由に無条件リロードしない。
- 新SWへの切り替えでも、取り込み・編集・保存中に強制リロードしない。
- アプリ本体の世代を混在させない更新方式を採用し、更新適用は安全なタイミングで行う。
- 同期ペイロードは復元可能な保留状態を確保するまでURLから消さない。
- sessionStorage等に保留する場合は例外処理を行い、保存失敗時はハッシュを残すなどの救済経路を設ける。
- 確定・キャンセル後は保留データを削除し、再読み込みによる二重取り込みを防ぐ。
- 保留データを通常の共有URLやログへ混入させない。

完了条件: 同期URLを開く→取り込み確認待ち→SW制御開始／更新という順序でも取り込みを継続できる。

### FIX-07: ストレージ障害を表示停止へ波及させない

対象: `public/sw.js`、`src/lib/opfsTileCache.ts`。

- caches.open／match／OPFSの読み出し失敗は分類して記録し、通常はキャッシュミスとしてネットワークへ進める。
- 保存失敗によって、取得済みの正常なデータまで呼び出し元へ返せなくなる構造を避ける。
- OPFSの初期化・読み出しには有限の待機時間を設ける。
- timeout後の古い操作完了は、新しいハンドルや世代を上書きしない。
- 一時的に無効となったハンドル・Promiseは再初期化可能にする。
- 停止が続くバックエンドは、そのセッションで一時的に使用を控える等、毎回同じ長時間待機を繰り返さない。
- すべての永続保存先が使えなくても、メモリとネットワークで閲覧を継続し、保存状態を正しく示す。

完了条件: Cache APIが拒否し、OPFSが未完了でも、期限後にネットワーク取得へ進み、正常なデータを表示できる。

### FIX-08: 気象カタログを保存・更新・部分復旧する

対象: `jmaNowcastClient.ts` fetchJMANowcastCatalog、`jaxaClient.ts`、Appのカタログ保持処理、SWのJSON経路。

- 成功したカタログを構造検証して保存し、取得日時・観測時刻・形式versionを保持する。
- 保存失敗はオンライン取得の成功を妨げない。
- N1実況を主経路とし、N2／rasrfの失敗で利用可能な実況まで捨てない。
- 空配列・不正JSONからbasetime／validtimeがない架空のフレームを生成しない。
- カタログ取得の各要求には期限を設ける。
- 起動時、期限経過時、前面復帰時、online復帰時、手動再試行で更新できるようにする。複数イベントによる同時更新は統合する。
- JMAの更新確認間隔は初期値5分を目安に設定化し、既存データの有効性と提供元の更新条件を踏まえて調整する。
- 保存済みカタログへフォールバックした場合は、その日時と更新失敗を明示し、古い実況を無条件に「現在」と呼ばない。
- 更新後の選択位置はindexでなく日時で引き継ぐ。対象日時がなくなった場合の選択規則を明示する。
- 長時間利用時に、GSMaPのImageCollection内部の古い情報も更新可能にする。

完了条件: オンラインで保存→アプリ再読み込み→オフラインで保存済みカタログを復元できる。N2失敗時もN1が表示でき、更新後に正しい時刻のデータへ切り替わる。

### FIX-09: SWの非同期保存を寿命管理へ登録する

対象: `public/sw.js` navigation／assets／weatherの各経路。

- response返却用Promiseと、保存・バックグラウンド更新用Promiseを整理する。
- 保存・更新処理をevent.waitUntilへ正しく登録し、Promiseのrejectも処理する。
- cache.putの完了後に容量整理を実施する。整理処理の無制限な並列起動を防ぐ。
- 取得失敗時に古い成功キャッシュを破壊しない。
- HTMLのHTTPエラー応答を正常なindex.htmlとして保存しない。
- オフラインfallbackが見つからない場合にundefinedを返さず、明確なエラー応答を返す。
- 本体の更新でHTMLとJS/CSSが不整合にならないことを確認する。

完了条件: 保存処理がwaitUntil対象として追跡され、書き込み失敗でも正常なネットワーク応答は利用できる。

### FIX-10: 件数・バイト数・容量不足からの回復を実装する

対象: TileCache、代替Cache Storage、SWの気象キャッシュ。

- OPFSと代替保存先の両方に、件数と合計バイト数の上限を設定する。
- 上限、タイムアウト、並列数は設定を一か所へ集約し、境界テストで小さい値へ差し替え可能にする。
- 更新時の差分サイズ、重複保存、削除済みファイルを整合的に扱う。
- QuotaExceededError時は、再取得可能な古いタイルを整理し、保存を限定再試行する。
- OPFSとCache Storageは容量制約を共有し得るため、保存先を変えるだけで復旧したと扱わない。
- 永続化が失敗した場合もメモリ表示を継続する。
- お気に入り、Undo、取り込み待ちデータをタイル整理の対象にしない。
- バックエンド能力確認前に空ファイルを大量生成しない。旧空ファイルは安全に整理する。
- 読み出し・書き込み・整理の競合で有効データを壊さない。

完了条件: 上限到達前後、更新・削除、容量例外で整合性が保たれ、整理後に保存を再試行できる。

### FIX-11: 最新の有効なコピーを読めるようにする

対象: TileCacheのOPFS／代替ストレージ間の整合性。

- OPFS更新失敗後に代替先へ保存した新しいデータを、次回起動でも読めるようにする。
- 保存先・更新世代・更新時刻を管理するか、保存方式をセッション単位で一貫させる等、優先順位を明確にする。
- 古いコピーの無効化は、新コピーの保存が成功した後に行う。
- 永続キャッシュからメモリへ昇格する際に、元の更新時刻を「今」に書き換えない。
- バックグラウンド更新失敗時は元データを保持し、期限情報を偽って更新しない。

完了条件: OPFSに旧版、代替先に新版がある状態で、メモリを空にしても新版を取得できる。

### FIX-12: キャンセル・期限・並列数を統一する

対象: MapLibre custom protocol、JMA画像・カタログ、JAXA取得、周辺地名取得、先読み処理。

- MapLibreのプロトコルハンドラーでAbortControllerを受け取り、TileCacheとfetchへsignalを渡す。
- 呼び出し時点でabort済みなら新たな通信を開始しない。
- 画面移動・ソース変更・アンマウントで不要になった処理をキャンセルする。
- 同一キーの要求を統合する場合、1利用者のキャンセルで他利用者の必要な取得を巻き込まない。利用者数・購読等の責任を明確にする。
- タイムアウトはレスポンスヘッダー受信まででなく、本文取得・デコード等、待機対象を明示して設定する。
- JMA画像はImage.onload／onerrorの無期限待ちを避ける。
- JAXA SDKのAPI名だけを見てキャンセル可能と判断しない。使用版の実装を確認する。
- SDKが要求単位の停止を提供しない場合は、並列数制限、期限切れ結果の無効化、必要に応じたWorker分離等で回復可能にする。共有SDKのglobal abortで無関係な要求を一括中断しない。
- 既に同梱しているJAXAモジュールを使えるのに、外部動的importの待機が初期表示を無期限に妨げない構成とする。
- 周辺地名取得のサーバー側timeout指定を、クライアントの通信期限と同一視しない。
- 待機や再試行をキャンセル可能にし、timer／listenerを解放する。

完了条件: キャンセル後に通信・再試行を増やさず、古い結果が画面を上書きしない。停止した1要求が以後の要求を永久に塞がない。

### FIX-13: 先読みを表示優先・予算付きにする

対象: Appの全フレーム先読み、合成画像・グリッド保持処理。

- 現在のフレームを最優先にし、前後の少数フレームだけを先読みする。初期値は前後2フレーム程度を出発点に調整可能とする。
- フレーム数だけでなくグリッド・画像等の保持バイト数でも上限管理する。
- 表示中のデータを保護し、不要なデータを退避・解放する。
- 表示要求が来たら先読みより優先する。背景化・ソース変更では先読みを停止する。
- 雨雲フレームのLRUには参照時の更新を含める。
- Data URLの長期保持を減らす場合は、Blob URLの利用中の寿命とrevokeのタイミングを管理する。切り替え直前に解放して表示を壊さない。
- ImageBitmap、canvas等、明示解放できる資源は不要時に解放する。
- JMAグリッドの1枚2.5MiBという実サイズを容量計算へ反映する。ブラウザ内部・GPUの使用量まで測れたと主張しない。

完了条件: 長いタイムラインでも保持量・先読み並列数が設定範囲に収まり、前面表示の要求が先読みによって待たされない。

### FIX-14: 保存データを外部入力と同等に検証する

対象: favoritesStorage、favoritesTransfer、Undo読込、移行処理。

- window.localStorageへの参照自体をtry内へ入れる。
- JSON形式、件数、ID、名前、座標の型・有限性・範囲、zoom/pitch/bearing、日付を検証する。
- JSON取り込み、同期URL、保存済み一覧、Undo、旧形式移行で検証規則を共通化する。
- 復元失敗と「保存データなし」を区別し、読込失敗後に空配列を自動保存しない。
- 不正項目を除外する場合は除外件数と理由分類を表示し、無警告で取り込み完了にしない。
- 通常登録も取り込みと同じ件数・名前上限を適用する。
- 圧縮ペイロードの展開後上限、ファイルサイズ上限など既存の保護を維持する。
- 破損データは、利用者が復旧・書き出しを検討できるよう可能な範囲で元データを保護する。

完了条件: storage getterの例外や不正座標でアプリ全体を落とさず、正常な項目は利用でき、除外・未保存状態が分かる。

## 5. テスト観点を先に整理する

テスト実装前に、以下の観点と追加発見事項をテスト計画へ記載する。各ケースには検証意図、初期状態、入力fixture、操作順序、期待結果、関連FIX-IDを記載する。

| 分類 | 正常系 | 異常系 | 境界値 | 状態遷移 |
|---|---|---|---|---|
| 機能 | 取得→保存→復元、Undo | 取得・保存失敗と再試行 | 全件成功／部分成功／全件失敗 | 失敗→回復、取り込み→取り消し |
| 非機能 | 表示優先の取得、制限内の先読み | 未完了Promise、低速、容量不足 | 並列数、件数、バイト数の上下限 | 前面→背景→復帰、online/offline |
| データ | キー・時刻・値の一致 | 不正JSON、破損画像、旧形式 | 0件、最大件数、座標範囲 | 旧コピー→新版、保存方式の移行 |
| UI | 保存・取得状態の正確な表示 | 未保存・欠測・更新失敗の可視化 | 全件欠測、空カタログ | 連続選択、ソース変更、SW更新 |

### 共通のテスト前提

- 外部APIは決定的なfixtureでモックし、実サービスの可用性をCIの合否条件にしない。
- 時刻はfake clock、応答順序は制御可能なPromise、容量は差し替え可能な設定で固定する。
- 単体テスト間でmodule singleton、in-flight、memory cache、timerを初期化する。
- ブラウザテストは独立したcontextで開始し、必要なSW・各ストレージだけを明示的にseedする。
- 永続化テストではページ再読み込みやcontext内の再起動でメモリを破棄し、永続データが残る条件を維持する。
- 移行・更新テストでは、旧データや旧SWを消してから開始しない。
- ローカルホストでは現行コードがSW解除・キャッシュ全削除を行うため、そのままでは更新・復元E2Eにならない。テスト時に本番相当のSW経路を有効化できる構成とし、意図せず無効化されていないことを検証する。
- 同一ブラウザプロファイルに対してテストを並列実行しない。ストレージ状態を共有するケースは順序を固定する。
- 単独実行と対象スイート通し実行の両方で、状態汚染の有無を確認する。

## 7. 自動ブラウザテストの実施範囲

E2Eは「対象ケースのみ」を基本とし、SW・保存・復元・読み込み競合に関する重要経路は、利用可能なデスクトップのChromiumとWebKitで実行する。全機能の全件実行は既定にしない。

対象の最低範囲:

- 正常な保存→再読み込み→復元。
- SW更新で代替キャッシュを保持。
- オフラインでカタログと保存済み画像を復元。
- 取り込み確認中のSW更新と、保存失敗時の表示。
- 時刻・ソースの連続変更と応答逆転。
- 欠測と降水量0の表示区別。

環境都合で一方のブラウザが実行できない場合は、理由・実行できた範囲・未実施ケースを明記する。WebKit自動テストを特定のiOS版での動作確認と表現しない。端末固有の評価は本書の開発者タスクに追加しない。

## 8. 診断情報と報告

エラー原因を分類できるよう、必要最小限の診断を追加する。

- アプリbuild、キャッシュ形式version、処理種別、保存先、成功／失敗、エラー分類。
- 件数、バイト数、所要時間、retry回数、要求世代、cache hit/miss/stale。
- 永続化可否、保存がメモリのみになった状態。
- SWの更新・有効化、カタログ更新の成否。

お気に入り名、正確な座標、JSON本文、同期URLのhash、秘密情報、不要なローカルパスは記録しない。タイル座標やURLが必要なテスト証跡は、合成fixtureの識別子を使う。

失敗時は原因を「テスト観点不足／データ問題／環境問題／実装問題」に分類し、再現手順・ログ・スクリーンショットまたはtrace・fixture IDを残す。タイムアウト延長だけで解消扱いにしない。

## 9. 実装の進め方と成果物

小さな変更単位で進め、各段階で対象テストを実行する。推奨順序は次のとおり。

1. テスト観点、状態・結果型、キーと世代管理を定義。
2. 誤表示・未保存・再試行不能を修正: FIX-02～05、14。
3. SW更新・取り込み保護・障害時の取得経路を修正: FIX-01、06、07、09。
4. カタログ保存更新とストレージ整合性・容量管理: FIX-08、10、11。
5. キャンセル・先読み・負荷制御: FIX-12、13。
6. 対象E2E、通し実行、ビルド、修正項目対応表の作成。

成果物:

- コード修正と回帰テスト。
- キャッシュ所有範囲、キー、期限、容量、移行・更新方式を説明する短い設計メモ。
- テスト観点とT01～T38の対応表。統合したケースは対応関係を明示する。
- FIX-01～14ごとの「修正箇所／検証結果／残存事項」。
- 実行コマンド、結果、対象コミット、使用したブラウザ・ランタイムの版。
- 未実施範囲と理由を含むPR用の変更説明。

ビルド・型検査は対象ソースを実際に検査するコマンドで行う。ルートtsconfigがfiles: []とproject referencesだけの場合、`tsc --noEmit`という名前上のlint成功だけで検査済みとしない。既存のbuildまたは適切なproject buildを使い、必要ならtypecheckスクリプトを整備する。

## 10. 完了条件

- FIX-01～14に実装・テスト・結果の対応がある。
- 取得失敗を「降水なし」、保存失敗を「保存完了」と表示しない。
- 選択時刻・ソース・画像・地点値が一貫する。
- 初回SW制御開始と更新で、取り込み待ち状態を失わない。
- SW更新で有効な代替キャッシュを削除しない。
- 一度の通信・ストレージ失敗から、ページ全体の再読み込みに頼らず回復可能。
- キャッシュ容量・メモリ保持・並列処理・再試行に上限がある。
- 既存お気に入りとUndoが移行・容量整理・失敗処理で失われない。
- 必須回帰ケース、対象ブラウザテスト、型検査・ビルドの結果を報告する。
- 未実施を成功と記載せず、未解消の重大問題があれば完了扱いにしない。
- 「iOSの問題を完全解消した」とは記載せず、「本書の実装・自動検証範囲を完了」と報告する。
