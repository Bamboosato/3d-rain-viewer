# JMA配信member反映 修正・検証結果

## 対象と原因

対象はPR #18の `26e894ab3341abf93f95c0835c5101819310e999` からの修正差分。本報告は本番反映前の検証結果。iPhone実機確認は利用者が担当する。

配信一覧は降水短時間予報の一部に `member: immed` を指定するが、旧実装はそのフィールドを保持せず、画像URLを常に `none` で組み立てていた。調査時、同じ発表時刻・予報対象時刻・タイルについて `none` は404、`immed` は200を確認した。前回のテスト用配信データにはこの違いがなく、memberを間違えたURLにも正常画像を返していたため検出できなかった。実装問題とテストデータの不足に分類する。

## 修正

- N1/N2/rasrfの配信一覧からmemberを読み、フレーム・保存カタログ・画像URLまで伝える。時刻や「6時間まで」等の固定条件から推測せず、配信一覧の指定を使う。
- `none` / `immed` のみ許可する。配信一覧と旧形式の省略は従来の `none` として扱い、不正な値はカタログから除外する。画像取得へ直接渡されても通信前に拒否する。
- `none` のフレームキー `jma:{dataset}:{basetime}:{validtime}:v1` は維持する。`immed` は `jma:{dataset}:{basetime}:{validtime}:immed:v2` とし、同じ発表・対象時刻でも別の画像として扱う。実行中要求もこのキーで分離される。
- 保存先 `rain3d_jma_catalog_v1` は維持し、本文version 2でmemberを明示保存する。旧versionなし/1を読み込み、member省略を `none` へ復元する。version 2でのmember欠落・不正値は拒否する。
- SWは従来どおり完全URLをキーにする。`none` URL、SW世代、OPFS、地図・標高キャッシュは変更せず、一括削除や全件移行を行わない。
- E2E配信fixtureにmemberを追加し、指定の違うURLには404を返す。これにより単に「予報時刻が表示できる」だけで誤ったURLを見逃さない。

## テスト観点

| 区分 | 検証する意図 |
|---|---|
| 機能・正常系 | 配信一覧から実画像取得まで指定を保持する。実況・ナウキャストの省略noneも維持する |
| データ・境界 | +1時間none→+1時間30分immed、+6時間immed→+7時間noneの切り替えを確認する |
| データ・互換性 | 旧カタログ・同時刻の旧noneキャッシュ・新immedキャッシュが混在しても誤hitや削除をしない |
| 異常系 | 不正memberを通信前に拒否する。404後、memberだけが変わった同じ対象時刻を新しい要求として再取得する |
| 状態遷移・UI | オフライン再起動、キャッシュ再訪、継続失敗時の時刻復帰・再生停止・ステータス行非表示を確認する |
| 非機能 | 初回の新しい予報画像は20枚を各1回取得する。メモリキャッシュ再訪で通信を増やさず、蓄積キャッシュの全走査を増やさない |

## 確認結果

- `npx vitest run`: 22ファイル・165件成功。実カタログ関数、実画像ローダー、Appのカタログ再解決を使用した。画像ローダーではmemberごとに20URLすべてと返却キーを検証した。
- `npm run build`: TypeScriptを含め成功。既存の大きなチャンク警告のみ。
- 対象E2EはWindowsのChromium/WebKit、workers=1で順次実施。実MapLibre・実SW・CacheStorageを使い、外部配信境界のみfixtureへ置き換えた。
- 対象は `MEMBER|FORECAST observation|FORECAST missing|FORECAST failed autoplay` の各ブラウザ4ケース、計8ケース。初回は7件成功・新規ケース1件の前提誤りで失敗し、下記の修正後に新規ケースを両ブラウザで再確認した。さらに旧カタログの完全オフライン確認を追加した最終実行も2件成功（全体33.4秒）。全対象ケースの成功を確認済み。
- +1時間/+1時間30分、+6/+7時間の全20タイルのURL指定を確認し、member不一致による404は0。新しいimmed/+7時間画像は各1回の取得。メモリキャッシュ再訪で要求数は増えない。
- 同じ日時の旧none URLに識別用データを残した状態でimmedを取得でき、その旧データと別用途のCacheStorageが維持された。新カタログで保存済みimmed/noneをオフライン再表示できた。
- version 1・memberなしの旧カタログ形状でも、保存済みnone画像を完全オフラインで再起動後に表示できた。
- 既存の予報境界、404によるカタログ再解決、自動再生失敗時の復帰も確認した。

初回のE2Eでは、1時間先の画像が初回表示とreloadの両方で先読みされ、既存SWが再検証する場合にも1回と期待して失敗した。traceの要求記録から、重複したのは初期先読み対象のnowcastのみで各URL最大2回と確認した。テストを2回の訪問という前提に合わせ、その時刻だけ上限2回とした。新しいimmed/+7時間画像は上限1回、メモリ再訪は増加0の条件を維持している。

## 実配信の少数確認

2026-11-10の確認時、気象庁の公開カタログが指定する次の代表画像を各1枚だけ取得し、いずれも200・image/pngだった。実機動作や全タイルの証明ではない。

| 発表時刻UTC | 予報対象UTC | member | HTTP | 本文byte |
|---|---|---|---|---|
| 20261110045000 | 20261110105000 | immed | 200 | 1,868 |
| 20261110040000 | 20261110110000 | none | 200 | 1,011 |

取得先は [気象庁rasrf配信一覧](https://www.jma.go.jp/bosai/jmatile/data/rasrf/targetTimes.json) の指定を使用した `surf/rasrf/6/56/25.png`。異なる発表時刻を使うため、境界は端末の現在時刻から厳密な6/7時間になるとは限らない。

## 制約と引き渡し

- 旧実装で取得できていなかったimmed画像は、オンラインでの初回取得が必要。旧カタログにないmemberを推測してオフラインデータを生成しない。既存none画像を一括再取得する変更はない。
- 新しいカタログ本文version 2は旧アプリでは読めないため、旧版へロールバックした場合はオンラインでのカタログ再取得が必要になることがある。今回の新アプリは旧カタログを読み込める。
- E2E全件・長時間耐久・地図PERFは未実施。地図キャッシュ/protocol/SW処理を変更していないため、確認はmemberと既存雨雲キャッシュに絞った。蓄積キャッシュの単体性能回帰は全体テストで成功し、既存metricsの内容は不変。
- iPhone PWAは未確認。本番反映後、キャッシュを削除せず1時間先付近・6〜7時間先を往復し、画像と日時の切り替え、同じ時刻への再訪を確認する。自動再生で該当境界を越えられることも確認する。
