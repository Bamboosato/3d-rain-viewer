## 3. テスト設計の共通条件

ケースの詳細化前に、次の観点と追加発見事項をテスト計画へ記載する。各ケースに意図、初期状態、fixture ID、操作順、期待結果、関連ADD/FIX/T-ID、証跡の保存先を付ける。

| 観点 | 正常系 | 異常系 | 境界値 | 状態遷移 |
|---|---|---|---|---|
| 機能 | 保存・復元・再取得 | 保存拒否・HTTP失敗・デコード失敗 | 全成功・部分成功・全失敗 | 取り込み→編集→Undo→再起動 |
| 非機能 | 表示優先・取得統合 | 停止Promise・低速・Quota | 件数・バイト・並列数・期限 | cancel・背景化・online復帰 |
| データ | キー・時刻・保存内容一致 | 不正JSON・日時・Undo・画像 | 100/101件、500/501件、50/51/60/61文字と採用上限前後 | 旧形式→移行、旧コピー→新版 |
| UI | 画像・値・時刻と保存結果の一致 | 未保存・欠測・部分障害・更新失敗 | 空一覧・全欠測・地図準備前 | A→B選択・ソース切替・SW更新 |

- 外部APIと画像は決定的fixtureで制御し、実サービスの可用性をCIの合否条件にしない。
- 時刻はfake clock、応答逆転は制御可能なPromise、容量と並列数は小さい設定値で再現する。実時間sleepによる順序依存を避ける。
- テスト間でmodule singleton、キャッシュ、timer、listener、storageを初期化する。未完了の非同期処理を次ケースへ持ち越さない。
- 保存と復元のテストはメモリを破棄する。単に保存関数の返値や同じReact stateを読むだけで完了としない。
- 更新・移行テストでは旧SW・旧保存データをseedし、事前削除しない。
- 同一実機・ブラウザプロファイルへのスクリプト並列実行は禁止。E2Eは`workers: 1`とし、contextの初期状態を明示する。
- 状態依存の重要ケースは単独実行と対象スイート通し実行の両方で確認する。フレークは状態汚染、非同期競合、外部通信、環境差の仮説ごとに切り分ける。
- 再現テストの意図を正式な回帰テストへ移す。APIを変更する場合、旧関数名や実装形状へのassertは置換してよいが、利用者に必要な期待結果を弱めない。特にR04は、名前上限を拡張して対応するなら「保存成功かつ全内容を復元できる」を検証する。

## 4. 個別の追加修正

### ADD-01 無警告のデータ欠落を止める

**優先度:** P0 致命。関連: FIX-03/14、T16/19/35/37/38、R03/R04。

**対象と問題:** `favoritesStorage.ts`の`filterAndValidateFavorites`と保存／読込API、`favoritesTransfer.ts`の正規化・上限、Appの通常登録、取り込み確認UI。保存側100件・50文字と取り込み側500件・60文字が一致せず、保存APIが除外件数を無視して成功を返す。

**再現手順:**

1. 有効なお気に入り100件を保存する。
2. Appと同じく新規1件を先頭へ加え、101件を通常保存する。
3. 成功が返る一方、起動用loaderで読み出すと既存の末尾1件が欠落する（R03）。
4. 別の初期状態で51文字の名前を1件保存する。成功が返るが保存件数は0になる（R04）。
5. 101件以上／51～60文字を含む取り込みを行い、確認・完了表示と再読込結果を比較する。このUI経路は追加検証する。

**修正内容:**

- 通常登録、JSON、同期URL、保存済み一覧、Undo、旧形式移行の検証規則と上限を共通化する。ID、名前、座標、カメラ値、日付を含める。
- 上限値は既存の取り込み・保存データとの互換性を根拠に選び、設定と設計メモへ明記する。小さい方へ統一して既存データを切り捨てる対応は禁止。
- 新規入力の上限超過は保存前に通知する。除外・修正を伴う取り込みは件数と理由を確定前に表示する。旧データの救済・書き出し経路を確保する。
- 保存失敗／入力不正を成功と返さない。UIは永続化した確定内容を表示し、未保存のpreviewを確定一覧にしない。
- 読込失敗と保存データなしを区別し、破損・上限超過を理由に空配列や切り捨て一覧で元データを自動上書きしない。

**必要なテスト:** R03/R04の利用者挙動、採用上限の直前・一致・超過、既存の100/500件・50/60文字境界、部分不正、全件不正、破損Undo、旧形式、圧縮展開後／ファイルサイズ上限。通常登録とJSON／同期URLで同じ判定になることを確認する。

**完了条件:** 成功表示された一覧・件数・名前が再起動後も一致する。既存項目の無警告欠落がなく、拒否した操作では旧保存内容と入力を維持する。

### ADD-02 保存の正本と原子的な確定を統一する

**優先度:** P1 重大。関連: FIX-03/14、T16～19/35/37、R01/R02/R05/R06。

**対象と問題:** `favoritesStorage.ts`の同期／非同期loader、通常保存、atomic保存、Undo、App起動処理。atomicキー・従来キー・IndexedDBの優先順位と更新先が不一致で、起動時はlocalStorageしか読まない。

**再現手順:**

1. 旧一覧Aから一覧Bを取り込み、atomic保存する。その後通常保存でCへ更新し、起動用loaderを呼ぶ。CではなくBが返る（R01）。
2. A→B取り込み後にUndoを成功させて再読込する。AではなくBが返る（R02）。
3. IndexedDBを使用不可とし、atomicキーの書込みは成功、続く従来キー書込みをQuotaで失敗させる。失敗／ロールバックと返るが、読込結果は新一覧になる（R05）。
4. IndexedDBのcommitだけを成功させ、localStorage書込みを拒否する。保存成功後も起動用loaderの一覧は空になる（R06）。

**修正内容:**

- 正本、フォールバック条件、保存世代、起動時の選択規則を明確にする。古いコピーを固定優先しない。
- IndexedDBを正本とする場合はAppの起動も非同期復元へ接続する。localStorageを正本とする場合も、currentとundoの一貫した単一レコード契約を守る。
- 通常更新、取り込み、Undoで同じ正本を更新する。currentとundoの確定／消費は同一トランザクション等で一貫させる。
- commitの成否と互換ミラーの成否を区別し、確定済みなのにロールバックしたと報告しない。UIに表示する状態と再読込結果を一致させる。
- 旧一覧・Undo・バックアップ操作日時を検証して移行し、commit成功後にだけ移行済みとする。失敗時に旧データを削除しない。保存先間に異なる内容がある場合の回復規則も定める。

**必要なテスト:** R01/R02/R05/R06、保存先の使用可否4組合せ、各書込み段階の失敗、transaction abort、移行失敗→再試行、Undo失敗→再試行、commit直後の再起動、旧／新版混在。UI一覧と起動時復元を確認する。

**完了条件:** 一度成功した編集・削除・Undoは再起動で巻き戻らない。失敗報告と実際の確定状態が矛盾せず、復元に失敗したUndoと移行元が残る。

### ADD-03 お気に入り更新を直列化し保存失敗を表示する

**優先度:** P1 重大。関連: FIX-03、T16～18/21/37、R14。

**対象と問題:** Appの`handleSaveFavorite`、削除、取り込み適用、Undo、`Inspector`と`FavoritesSyncDialog`。保存callbackの依存配列に`favorites`がなく、保存失敗はconsoleのみ。Inspectorは保存結果を待たず編集を閉じる。

**再現手順:**

1. 有効なお気に入りAとBを保存し、AをInspectorで選択する。
2. 別項目Bを削除し、一覧から消えたことを確認する。
3. Aの名前を変更して保存する。古い一覧からBが復活する（R14）。
4. 別途、通常保存をQuota／権限例外で失敗させ、編集UIと通知を確認する。現状は失敗を画面へ伝えない。

**修正内容:**

- callbackの参照する状態を正しく更新するとともに、通常更新・削除・取り込み・Undoを同じキュー／トランザクション規則で直列化する。依存配列だけ直して完了としない。
- 更新操作は実行時の最新確定状態を基に計算する。保存前に作った古い一覧で後の操作を上書きしない。
- UI callbackを保存完了が分かる非同期契約にし、保存中・失敗・再試行を表示する。失敗時は入力を保持する。
- 取り込み確定後の`onApplyFavorites`等で不要な二重保存を起こさない。連打、閉じる、Undoとの競合も扱う。
- Reactのstate updater内に保存副作用を置かない。

**必要なテスト:** R14、追加と削除の応答逆転、通常保存と取り込みの競合、取り込み連打、保存中の閉じる操作、失敗→再試行。ユーザーに見える通知と未保存入力をassertする。

**完了条件:** 削除済み項目の復活や後の変更の消失がなく、保存失敗時に完了表示・入力消失が起きない。

### ADD-06 SWの保存失敗で正常な通信結果を失わない

**優先度:** P1 重大。関連: FIX-01/07/09、T01～03/27/28、R08/R09。

**対象と問題:** `public/sw.js`の気象画像経路。`caches.open/match`が保護されず、`cache.put`失敗がfetch失敗と同じcatchに入る。

**再現手順:**

1. 実SWソースのfetch handlerに合成JMA画像要求を渡す。ネットワークはHTTP 200とする。
2. `caches.open`をrejectすると、ネットワークへ進まず要求が失敗する（R08）。
3. cache miss、ネットワーク成功、`cache.put`だけrejectとすると、HTTP 200が`Response.error()`へ置き換わる（R09）。

**修正内容:**

- キャッシュopen/match失敗は通常キャッシュミスとして扱う。保存失敗と取得失敗を別の処理・分類にする。
- 正常な応答を保存完了から切り離して返し、保存・更新・整理を`event.waitUntil`で追跡する。rejectを処理し未処理例外を残さない。
- `cache.put`完了後に整理し、整理の同時実行を制御する。旧成功データを失敗応答で上書きしない。
- 所有prefix限定のactivate削除、背景タイル透過、HTMLのHTTPエラー非保存を維持する。fallbackなし／Cache API拒否時も明確な応答にする。

**対象と問題:** TileCache共有Promise、MapLibre protocol、JMA、JAXA SDK、周辺地名、retry/backoff。先頭利用者のsignalで共有取得を動かし、別利用者まで中断する。AW3D fetcherやAppの呼び出しではキャンセルが伝播しない。

**修正内容:**

**必要なテスト:** R07、初回失敗→成功、同時要求統合、1人／全員cancel、abort済み、取得中／backoff中cancel、本文停止、SDK停止、429、異常入力。次の要求が永久に塞がれないことを確認する。

**完了条件:** 必要な購読者の取得を維持し、不要な通信・再試行・旧画面更新を止める。停止した1要求で以後の利用が不能にならない。
