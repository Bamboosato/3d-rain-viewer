# 未来時刻の雨雲取得エラー調査・対応案

## 対象と結論

- 対象: `4417eb9e43aaa96a9ca23f605529b5e81802a876`（PR #16反映後）。製品コードは変更せず調査した。
- 利用者報告: iPhone実機で約10時間先を選択すると「選択時刻の取得に失敗しました。…」「雨雲データを取得できません。…」が表示され、スライダーを止めても残る。既報の利用環境はiPhone 13 Pro MaxのPWA。
- 一時的な取得失敗を自動回復させる仕組みと、不要な要求の抑制が不足している。内部エラーの通常画面への表示は取り除き、表示している雨雲の時刻・欠測状態は正しく伝える方針を推奨する。
- 発生当時のiPhoneのHTTP応答・通信ログは未取得。一時的な配信障害、通信不良、画像読込/デコード失敗のどれが最初の原因だったかは断定しない。

## 実装で確認した事実

1. **雨雲画像に自動リトライがない。** `src/lib/jmaNowcastClient.ts` の `loadTileImage` は画像を1回だけ読み込み、8秒のtimeout・画像エラー・不正な寸法をすべて `null` にする。`fetchJMANowcastRainLayer` は1フレーム20枚を並列取得し、全失敗時に例外を投げる。背景地図用の `fetchTileBytesWithRetry` はこの経路では使われない。カタログ取得も各URL1回・6秒timeoutで、即時の自動再試行はない。
2. **失敗をそのまま利用者向けエラーにしている。** `src/App.tsx` の `handleSelectTimeIndex` は失敗を捕捉すると選択時刻エラーを設定する。初期取得・カタログ更新の `initSourceTimeline` は雨雲データ取得エラーを設定し、共通の画面領域で表示する。5分ごと・オンライン復帰・画面復帰のカタログ更新はあるが、失敗した選択時刻を短時間で自動回復する制御はない。
3. **古い表示要求が残る。** スライダーの各 `onChange` で取得を開始する。世代番号は古い結果の画面反映を防ぐが、次の時刻を選んでも既存のforeground要求は中止しない。`FrameScheduler` は2フレーム並列で、foreground待機列は先着順・件数上限なし。最終的に選んだ時刻が、通過した時刻の後ろで待つ。1フレーム20枚なので最大2フレーム分40枚の画像読込が重なり得る。
4. **25秒の制限に待機列の滞在時間を含めていない。** `bounded` はスケジューラーで開始した後に適用する。期限に到達しても、それだけでは基礎処理のAbortControllerを中止しない。再試行を追加する場合は、待機も含む全体期限と基礎処理の停止が必要。
5. **選択時刻と表示内容の状態が混在する。** 失敗時は最後の正常画像とその日時を保持する一方、TimelineBarの「現在／予測」は選択位置から計算する。実況画像と実況日時に「予測」が付く状態を再現した。メッセージを消すだけでは、この誤解の可能性が残る。
6. **手動再試行にも二重の経路がある。** 画面の再試行ボタンは `refreshCatalog()` と古いリストに対する `handleSelectTimeIndex()` を同時に呼ぶ。カタログ更新effectのcleanupで全フレームを中止するため、無駄な開始・中断が生じる構造がある。自動回復の追加時は単一の経路へ整理する。
7. **テストデータが未来を含まない。** 現行 `e2e/server.mjs` の気象庁fixtureは実況1時刻、N2/rasrfは空配列。通常E2Eでは10時間先や予報切替の失敗・自動回復を検証できない。

なお、気象庁の7～15時間先の予報は1時間ごとの更新で、直近のナウキャストとは提供周期が異なる。カタログと画像の更新タイミング差は考慮すべき仮説だが、今回の実機障害の原因と確認できたわけではない。出典: [気象庁「今後の雨」](https://www.jma.go.jp/bosai/rain/rasrf.html)、[降水等のナウキャスト、降水短時間予報](https://www.data.jma.go.jp/developer/weatherdataguide/appendix/2-1-b.html)。

## 短時間の再現確認

先に選んだ観点: 正常な実況表示、未来時刻のみ一時失敗、配信回復後の状態遷移、連続選択の待機順序、表示時刻とラベルの整合性。外部配信と利用者データは変更していない。

| 検証 | 条件・結果 |
|---|---|
| 現在の気象庁配信 | N1/N2/rasrfのカタログはHTTP 200。代表的な近未来・長時間先のPNGもHTTP 200・PNG署名を確認。これは調査時点の代表URLの正常性であり、発生当時の配信状態や全領域の正常性の証明ではない |
| 約10時間先の一時失敗 | ローカルの実アプリで実況・近未来は正常、10時間先の20枚だけ503に固定。WindowsのChromium / WebKitの両方で選択時刻エラーを再現 |
| 配信回復後 | 503を正常画像へ切り替えて1.5秒観察。両ブラウザとも要求数20のまま、エラー表示が残った。コード上も短時間の再試行はない |
| 再選択後 | 実況へ戻して再度10時間先を選択。両ブラウザとも追加20枚を取得し、エラーが消え、日時が `11/09 15:00` から `11/10 01:00` に更新された |
| 失敗中の表示 | 両ブラウザとも以前の実況日時 `11/09 15:00` と「予測」が同時に表示された |
| 連続要求 | 実 `FrameScheduler` に8件を渡し、完了を制御。開始は0・1、0を解放すると次は2。最新の7は待機したまま。これはスケジューラーの動作確認であり、iPhone上の遅延時間測定ではない |

ブラウザ再現は、実MapLibreを含む既存ビルド・外部API境界の固定画像を使い、取得失敗を切り分けるためService Workerを無効化した独立コンテキストで順次実行した。SW・既存キャッシュを含む復旧動作とiPhone実機での同条件再現は未確認。再現用のスクリプトは一時実行で、製品・既存テストファイルには追加していない。

## 推奨対応（実装前の案）

### 優先度高: 自動回復と表示の整合性

- 通信エラー・timeout・429/5xxは、最初の取得に加えて最大2回を目安に、間隔を空けて再試行する。待機・通信・デコードを含む全体期限も設ける。具体的な間隔と上限は短い対象試験で決め、無限再試行や毎フレームの再取得を作らない。
- 画像の `onerror` だけではHTTPステータスを区別できない。HTTP取得と画像デコードの結果を分類できる経路へ整理し、失敗理由・回数・時間を内部診断へ残す。
- 404/410や古い発表時刻が疑われる場合、同じURLを繰り返すのではなく、カタログを1回更新して選択時刻を解決し直す。カタログが変わらない場合や非対応・デコード異常では短い間隔の無限再試行をしない。429の `Retry-After` が全体期限を超える場合は待機を延期する。
- 再試行は失敗した画像に限定し、同一フレーム内で取得済みの正常画像を保持する。既存の成功フレーム・SWキャッシュを利用し、URLへの乱数付与や全キャッシュ削除は行わない。
- オフライン中は繰り返さず、オンライン復帰時に最新の選択だけ再開する。選択変更・ソース切替・破棄で不要な再試行と後続処理を停止する。画面非表示中は先読み・再試行を止め、復帰時に必要性を再評価する。
- 内部の取得失敗・timeout・キャンセルを通常画面のメッセージ／トーストに表示しない。最後の正常画像を維持し、時刻表示と「実況／予測」は実際に表示しているデータに合わせる。選択時刻と表示時刻が異なる間はタイムライン内の控えめな取得中・更新待ち状態で区別する。
- 初回からデータがない場合や対象地点が欠測の場合は、降水量を0として表示しない。「未取得／欠測」等のデータ状態は内部エラーとは区別して維持する。お気に入り保存失敗などの別機能の通知には影響させない。

### 優先度高: 連続操作時の負荷抑制

- スライダー位置は即座に反映し、画像取得は短い間隔で最新の選択へ集約する。古いforeground待機要求を破棄し、実行中も不要なら停止する。同一時刻の共有要求は再利用する。
- 同時フレーム数に加え、タイル並列数・待機件数・保持byte数・再試行回数を制限する。先読みは表示要求より後にする。単純に再試行を足して通信量を増やさない。
- 初期表示・手動選択・定期更新・復帰・再試行を同じ取得制御へ集約する。新カタログの確定後に対象を選び直し、旧リストへの取得と競合させない。
- 自動再生でも未完了の時刻を無制限に積まず、最新位置への集約または表示完了を待つ方針を明確にする。

### 必要な対象テスト・完了条件

- 正常系: 実況、+10分、+1時間、+6/+7時間境界、+10時間、最遠予報を有効なfixtureで表示できる。
- 異常系: 一時503・timeout・429から設定回数内で自動回復する。404/410ではカタログ更新へ進む。継続障害・全欠測・一部欠測・デコード異常・オフラインを区別する。
- 状態遷移: 連続スライド、再生、ソース切替、非表示→復帰、取得中のカタログ更新、古い応答の後着で最新の表示を壊さない。キャンセル後に再試行が再開しない。
- UI: 内部エラー文が表示されず、日時・実況/予測・地点降水量が表示フレームと一致する。前の画像を未来のデータや無降水と誤認させない。
- 性能・データ: 成功キャッシュの再利用、失敗画像だけの再取得、待機列と同時数・byte予算を計測する。地図キャッシュは保持する。SWを変更する場合は実SWハンドラーのテストと既存PERFケースも対象とする。
- Chromium / WebKitの対象E2Eを順次実行し、全件や長時間試験は既定にしない。最終的なiPhone PWA確認は利用者が担当する。
