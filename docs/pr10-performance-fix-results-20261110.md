# PR #10 性能改善の実装・検証結果

2026-11-10（JST）。対象: [性能調査報告](pr10-performance-review-20261110.md) PERF-01～06。基準コミットは`dda9efc`。修正はローカル差分であり、本番反映・PR作成・マージは今回行っていない。

## 1. 修正内容

| 調査項目 | 実装した改善 |
|---|---|
| PERF-01 読込の全件探索 | OPFS/代替CacheStorageのファイル・キー一覧を保存先/区分ごとの共有索引に集約。通常のタイル読込は同じ索引を参照する。旧固定名・PR #10の世代名・新しいサイズ付き世代名を読める |
| PERF-02 保存時の全件調査 | 新ファイル名/URLに世代とbyte数を保存し、書込み時に容量を差分更新。サイズ不明の旧データは最大4件ずつ監査する。全件へのgetFile/arrayBufferの同時発行を撤去 |
| PERF-03 SWの全本文再読込 | worker内で容量索引を共有し、新規本文だけを1回測定。サイズは応答ヘッダーに保存。旧レスポンスは最大4件ずつ移行する |
| PERF-04 timeout/cancel | 永続読込の待機にsignalを伝播。索引作成の期限後に列挙を継続しない。索引失敗時も旧固定名へ直接アクセス。正常なコピーを得たら、もう一方を待つ時間は最大25msに制限 |
| PERF-05 保存見送りと画面表示 | キュー32件超過分はメモリLRU内のデータを参照するキーとして保留し、空きができたら再投入。`deferred`と保存不能を区別。地図キャッシュの内部エラー表示と、そのためのReact state更新を撤去。お気に入りの保存失敗通知は維持 |
| PERF-06 診断 | 永続hitの保存先・byte数と読込時間、保留件数を内部イベントへ追加。検証ではAPI呼出し数と実ブラウザのイベントを採取。常時集計ダッシュボードや端末のp95可視化は追加していない |

追加で、非BFCacheの`pagehide`では古い画面の保存待ち・保留キューと共有通信を終了する。短いWebKit試験で、再読込前の保留保存が古いdocumentの保存APIで失敗し、新しい画面へエラー記録を流す状態を検出したため対処した。開始済みの書込みそのものは完了し得るが、古い画面から後続保存を続けたり失敗通知を流したりしない。

## 2. 検証観点と前提

| 観点 | 正常系 | 異常系 | 境界値 | 状態遷移 |
|---|---|---|---|---|
| 機能 | 永続hit・保存・再読込 | 索引停止、別保存先停止 | 保存待ち32件超過 | 取得→保存→再訪 |
| 非機能 | タイル当たりI/Oを削減 | timeout後の残存探索 | 1,200ファイル/600レスポンス | 連続パン・ズーム→取消 |
| データ | 旧キャッシュ互換・世代保護 | 古いcloseの遅延 | byte上限、サイズ不明データ | 旧形式→段階移行 |
| UI | 地図更新と入力保持 | 内部キャッシュエラー非表示 | 40枚の連続要求 | 操作→reload→永続hit |

合成試験は実際の取得関数とSWスクリプトを使用し、API境界だけをfixture化した。旧報告の同じ件数・データ量と比較している。停止・取消は制御Promiseと仮想時計で固定。本文byte数はAPIで読む量であり、iPhoneの物理I/O・メモリ実測ではない。

## 3. 蓄積キャッシュの改善比較

| 条件・指標 | PR #10 | 修正後 |
|---|---:|---:|
| OPFS 1,200枚から20枚取得: ファイル名探索 | 24,000件（20回） | 1,200件（共有1回） |
| 同上: 代替キャッシュキー一覧取得 | 20回 | 1回 |
| 同上: ネットワーク再取得 | 0 | 0 |
| OPFS 1,200枚に1枚追加: 既存サイズ調査 | 1,201回のgetFile | 最大4回 |
| 代替600枚×100KBに1枚追加: 既存本文読込 | 60MB | 最大0.4MB（4件の旧データ移行） |
| SW 399枚×100KBに1枚追加: 既存本文読込 | 40MB相当（新規分も含む400件） | 既存最大0.4MB＋新規0.1MB |
| 正常OPFS＋代替一覧停止: 返却待ち | 2,500ms | 仮想時計30ms以内で返却確認（他方待ち上限25ms） |
| 索引停止後、存在する旧タイルのネットワーク再取得 | 1回 | 0回、直接読込で回復 |
| timeout後に解放した探索 | 1,200件まで継続 | 2件で停止 |
| 40枚の連続要求、保留解除後の永続保存 | 32枚、8枚取りこぼし | 40枚、8枚を保留後に再投入 |

20枚の読込における探索件数は95%削減。代替キャッシュの当該保存時の既存本文読込量は99.3%削減。どちらも**処理量**の改善率であり、実機表示速度が同じ割合で向上したという意味ではない。

単体/コンポーネント/SW回帰は**105件成功**。追加した性能回帰9件には、上記の比較条件、要求cancel、reloadによる古い保存キューの終了を含む。既存のお気に入り・Undo・世代保護・quota等も通しで確認した。

証跡: [性能回帰コード](../tests/cache_performance.test.ts)、[処理量](../output/implementation-20261110-performance/metrics.json)、[単体結果](../output/implementation-20261110-performance/unit-results.json)。比較元は[調査時の計測値](../output/review-20261110-performance/metrics.json)。

## 4. 短時間のブラウザ確認

E2Eは今回追加したパン/ズーム/再読込の**1ケース×Chromium/WebKit**に限定した。全件E2E・長時間耐久試験・実外部地図APIへの負荷試験は実施していない。利用者がiPhone実機確認を担当すること、今回のリスクが保存経路と画面更新に集中することから、この範囲を選定した。各ブラウザは`workers=1`で直列実行した。

前回と異なり、OSMタイルをabortせず256pxの有効PNGを返し、標高SDKもこのケースでは有効データを返す。実際のMapLibre・カスタムprotocol・OPFS/CacheStorageを使い、ドラッグ→ズーム→逆方向ドラッグ→ズーム→reloadを実行する。色/地形は固定の合成データであり、実地図の見た目の受入ではない。

確認事項:

- 操作による新規タイルの取得と保存が進む。
- ページをreloadしてメモリを破棄した後、OPFSまたは代替キャッシュからhitする。
- 内部`memory-only`イベントを注入しても通常画面に保存エラーが出ない。
- reload後に古い画面由来の保存不能イベントを流さない。

最終結果は[対象E2E結果](../output/implementation-20261110-performance/e2e-results.json)と[ブラウザ別イベント集計](../output/implementation-20261110-performance/browser-summary.json)に記録する。最初の実行で検出した旧documentの問題は修正し、同じ対象ケースで再確認した。実行時間は試験全体の所要時間であり、地図の表示時間の測定値ではない。

実行コマンド:

```powershell
npm test -- --reporter=json --outputFile=output/implementation-20261110-performance/unit-results.json
npm run build
$env:PLAYWRIGHT_JSON_OUTPUT_FILE='output/implementation-20261110-performance/e2e-results.json'
npm run test:e2e -- --grep PERF --reporter=list,json
```

Node v24.22.1 / Vitest 5.1.0 / Playwright 1.65.0、Windows上で実行。型検査を含むbuildも成功。既存の500kB超chunk警告は残る。

## 5. 設計上の範囲と実機で見る点

- 索引は現在のdocument/worker内で共有し、起動ごとに1回作成する。永続索引DBを追加したわけではない。非常に大きい/壊れた一覧は期限を設け、旧固定名への直接読込で救済する。
- サイズ不明の旧キャッシュは少量ずつ移行するため、旧全体のbyte上限の厳密評価は移行完了後になる。移行途中も件数、既知byte数、Quota時の限定整理を使用する。表示を止めて全本文を読む方法は採用しない。
- 遅い保存先にしか最新版がない場合は、まず利用可能なコピーを表示し、後着の新版を次回メモリ読込へ反映する。停止中の保存先まで含めた厳密な最新性より表示の継続を優先する。
- 保存保留はメモリLRUの範囲内。大量操作でメモリから追い出されたデータや、ページを閉じる前に完了しない全タイルの永続化までは保証しない。地図タイルは再生成可能なキャッシュとして扱う。
- 複数タブの保存索引をリアルタイム同期する機能、長時間のOSメモリ圧迫、iPhoneのディスク容量飽和は今回の短時間試験に含めない。

本番反映後のiPhone確認では、**既存キャッシュを消さずに**起動→同じ範囲の往復→連続パン/ピンチ→再起動を確認する。初回索引作成時と同じ範囲への再訪を分け、内部保存警告が出ないことを確認する。まだ遅い場合はiOS版・通信条件・初回か再訪かを添えると切り分けしやすい。WebKitランナーの成功をiPhone実機での確認済みとは扱わない。
