## 4. テスト観点と共通前提

詳細ケースを書く前に、次の観点を計画へ記載する。各ケースに意図、初期状態、fixture ID、操作順、期待結果、関連RE/ADD/FIX/T-ID、証跡を付ける。

| 観点 | 正常系 | 異常系 | 境界値 | 状態遷移 |
|---|---|---|---|---|
| 機能 | 保存・再起動復元・Undo | 片側保存失敗・rollback失敗 | 空の最新版／非空の旧版 | 通常保存→取り込み→再起動 |
| 非機能 | 取得統合・表示優先 | 未完了Promise・Quota・低速 | 件数・バイト・同時数・期限 | 全員cancel→再要求、背景→復帰 |
| データ | 保存世代・画像と値の一致 | 旧形式・不正日付・破損Undo | 100/101/500件、50/51/60文字、2月末 | 旧保存→移行、IDB/LS世代逆転 |
| UI | 正確な保存状態・欠測表示 | 部分失敗・更新失敗 | 地図準備前・初期化中の操作 | 選択後に旧エラー、保存中SW更新 |

- 外部API、地図、SDK等の境界だけを決定的fixtureで置換する。検証対象の保存・採用・削除ロジックをテスト内へ複写しない。
- 時刻はfake clock、応答順は制御可能なPromiseで固定し、実時間sleepで順序を作らない。
- 旧データ／旧SWをseedするテストで、事前に対象データやcacheを削除しない。各ケースの前提をコードで保証する。
- 再起動テストはReact state、ref、module singleton、memoryFavoritesCacheを破棄する。正式E2Eでは同一context内のページ再読込等で永続データだけを残す。
- 同一実機・同一ブラウザプロファイルでスクリプトを並列実行しない。E2Eは`workers: 1`。テスト間のtimer/listener/未完了処理も解放する。
- 重要な状態遷移は単独・対象スイート通しの両方で実行する。フレークは状態汚染・応答順序・外部通信・環境差の仮説ごとに調べる。
- 再現コードは正式回帰へ移す。API変更時は利用者の期待結果を維持してテストを更新する。特に「失敗なら旧版、commit成功なら新版」という契約へ変更した場合、旧テストの失敗返値だけを固定しない。

## 5. 残存事項の修正指示

### RE-01 旧保存データを無警告に切り捨てない

**優先度:** P0。関連: ADD-01、FIX-03/14、T19/35/37/38。証拠: S01/S02/S05、自動再現済み。

**対象:** `favoritesStorage.ts`の検証・同期／非同期読込、`favoritesTransfer.ts`の`sanitizeName`と取り込み、通常編集・書き出し。

**維持する修正:** 新規入力の上限拒否と保存失敗契約。上限を超える入力を保存成功として切り捨てない。

**再現手順:**

1. 旧localStorageキーへ有効な101件を保存し、起動用loaderで読む。
2. 読み出せた先頭項目の名前だけを変え、通常保存する。旧101件目が元の永続データから消える（S01）。
3. 別ケースで旧60文字名の項目と短い名前の項目をseedする。短い方だけ編集保存すると、長い名前の項目が消える（S02）。
4. 60文字名を含むJSONを取り込むと、エラーや確認なしに50文字へ短縮される（S05）。

**修正内容:**

- 旧保存データの件数・名前制限超過を、新規入力の拒否と分けて扱う。元データを保持し、除外・制限超過・読込失敗を呼出し元とUIへ返す。
- 旧データを制限内の配列へ縮めてから通常保存しない。互換読込、救済用書き出し、編集の一時拒否等、情報を失わない処理を実装する。
- 名前の短縮や不正項目除外を伴う取り込みは変更内容と理由を確定前に表示する。無警告の正規化を成功扱いにしない。
- ID、日付、座標、カメラ値の検証も全入口で共通化する。破損Undoや読込失敗を空一覧と同じ扱いにしない。

**必要なテスト:** S01/S02/S05、旧500件、50/51/60文字、部分不正／全件不正、旧Undo、破損JSON、取り込み・書き出し往復、ファイル／展開後サイズ境界。正常な新規100件・50文字、超過拒否の既存テストも維持する。

**完了条件:** 別項目の編集・削除・再保存で旧項目や名前の情報が失われない。変更／除外が必要な場合は利用者に明示し、救済可能な元データを保護する。

### RE-02 最新の空一覧を含めて正本から復元する

**優先度:** P1。関連: ADD-02、FIX-03/14、T16/18/19。証拠: A01/A02、自動再現済み。

**対象:** Appの非同期初期読込（レビュー時99～103行）、各保存先の世代管理・移行、`memoryFavoritesCache`。

**維持する修正:** 非同期IDB読込の入口と通常成功時の保存内容更新。ただし同一セッションのmemory cache一致を再起動保証としない。

**再現手順:**

1. localStorageへ旧一覧Aを残す。
2. IndexedDB commitは成功、localStorage書込みだけQuotaとする。
3. 全削除を保存してsuccessを得る。メモリを破棄してAppを起動するとAが再表示される（A01）。
4. 全削除の代わりに新一覧Bを保存しても、古いlocalStorageが非空だとAの表示を維持する（A02）。

**修正内容:**

- 正本、fallback条件、保存世代／commit、起動時の選択規則を決める。「現在の一覧が空ならIDBを採用」の判定を廃止する。
- 空配列を正当な保存結果として扱い、データなし・読込失敗と区別する。
- React stateとfavoritesRefへ同じ確定一覧を反映する。初期復元完了前の操作を待機させる等、通常更新キューとの競合を防ぐ。
- 一覧・Undo・書き出し操作日時を含む旧形式移行を実装し、成功確認後に移行済みとする。異なるコピーがある場合の選択と復旧方法を明記する。

**必要なテスト:** A01/A02、IDBのみ成功／LSのみ成功／両成功／両失敗、最新空一覧、遅延初期読込中の編集、保存先回復、旧形式移行失敗→再試行、メモリ破棄後の復元。実ページ再読込でも確認する。

**完了条件:** 成功した編集・全削除が再起動で巻き戻らない。保存先の可否変化でも、正本の最新版とUIが一致する。

### RE-03 取り込みとUndoのcommitまで同じキューへ入れる

**優先度:** P1。関連: ADD-03、FIX-03、T16～18。証拠: D01、自動再現済み。

**対象:** Appの`runSerializedFavoritesOp`／`handleApplyFavorites`、`FavoritesSyncDialog`の取り込みとUndo。

**維持する修正:** 通常追加・編集・削除の直列化、Inspectorの保存結果待機と失敗時入力保持。

**再現手順:**

1. お気に入りAを表示し、名前をold-Aからedited-Aへ変更して保存する。保存処理を保留する。
2. Bを追加する有効な同期URLを受け取り、取り込みを確定する。
3. 取り込みのcommitを先に完了し、通常保存を後から完了する。
4. 現状は画面がold-A＋new-B、永続データがedited-Aのみとなる。取り込み成功でもBを失う（D01）。

**修正内容:**

- 取り込み・Undoの永続保存自体を通常更新と同じキューへ移す。保存後のstate反映だけをキューに入れる構造を廃止する。
- merge結果とUndoはキュー実行時の最新確定一覧から作る。確認時以降に変更があり、結果が変わる場合は確認内容を更新する。
- commit、Undo作成／消費、確定一覧の反映を一貫した操作にする。連打・閉じる・失敗再試行の状態を扱う。
- 削除の成否もUIで受け取り、失敗を無言で終わらせない。二重保存やstate updater内の副作用を避ける。

**必要なテスト:** D01、通常更新と取り込み／Undoの両応答順、取り込み連打、保存中の閉じる、取り込み後Undo→再起動、削除失敗。D01ではUIと永続データがともにedited-A＋new-Bとなり、Undoは最新の取り込み前一覧へ戻ることを確認する。

**完了条件:** すべての更新が同じ順序で確定し、成功表示・一覧・Undo・再起動結果が一致する。

### RE-04 commitと保存結果の契約を一致させる

**優先度:** P1。関連: ADD-02、FIX-03/14、T16～19/35。証拠: S03/S04、自動再現済み。

**対象:** `favoritesStorage.ts`の通常保存、atomic保存、rollback、storage読出し。

**維持する修正:** 通常成功時のatomicキー更新。複数キーの復元を試みたこと自体を原子性の保証にしない。

**再現手順:**

1. 旧一覧を保存する。
2. 新atomicレコードの最初の書込みだけ成功させ、互換キーとrollbackの後続書込みを継続的に拒否する。
3. APIは失敗・ロールバックした旨を返すが、メモリ破棄後の読込は新一覧になる（S03）。
4. 別ケースでlocalStorage取得自体は成功、`getItem`だけを拒否する。try外の読出しからPromise rejectが漏れる（S04）。

**修正内容:**

- 単一レコードまたは同一transactionをcommit境界とする。複数キーを逐次更新し、catchで戻す方式だけに依存しない。
- 正本のcommitと互換ミラーの更新を区別する。commit済みならその事実に即した成功結果、未確定なら旧状態を保持した失敗結果を返す。
- rollback失敗を無視して「完全ロールバック」と通知しない。保存内容が不確定な場合は再読込・回復を行い、誤った確定表示を防ぐ。
- storage getter・getItem・setItem・removeItem・transaction各段階の例外を契約内で処理する。

**必要なテスト:** S03/S04、各段階の失敗、commit後ミラー失敗、rollbackも拒否、transaction abort、両保存先に異なる世代、Undo復元失敗、再起動。新契約がcommit済みを成功と返す場合、S03は成功＋新版の整合性を検証する形へ更新してよい。

**完了条件:** 「失敗＋旧状態」または「commit成功＋新状態」が再起動後も一致し、操作結果と永続内容が矛盾しない。

### RE-05 画像と地点値を同一結果として採用する

**優先度:** P1。関連: ADD-04、FIX-05、T13～15。証拠: J01/A03は自動再現済み、地図準備経路はコード確認。

**対象:** `jaxaClient.ts`のactive Inspector更新、Appの採用・初期catch、MapViewerの準備完了・load handler。

**維持する修正:** 初期採用のactive更新呼出し、通常選択・ソース変更の世代番号、前回R11～R13の応答逆転防止。

**再現手順:**

1. GSMaPの1mm/hフレームを採用してInspector生成を完了する。
2. 20mm/hフレームを採用し、Appと同じく直後に地点値を読む。旧値1mm/hが返る（J01）。
3. 初期Aを保留してBを選択する。Bが未完了のままAを失敗させると、Bのloadingが解除される（A03）。
4. 地図生成前に雨雲結果を返すケース、load待ち中に複数結果を採用するケースを追加する。

**修正内容:**
