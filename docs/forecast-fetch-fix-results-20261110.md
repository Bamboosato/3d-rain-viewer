# 未来時刻の雨雲取得回復・修正結果

## 対象と修正

対象は `4417eb9e43aaa96a9ca23f605529b5e81802a876`（PR #16）からの作業ツリー差分。[調査報告書](forecast-fetch-investigation-20261110.md)に基づく修正で、製品コード・対象テスト・設計メモを更新した。本番反映前の検証結果であり、iPhone実機確認は利用者が担当する。

- JMA画像・カタログのHTTP取得を分類し、一時的な通信不良・timeout・429/5xxに対して追加最大2回の自動再試行を行う。画像のデコード異常・不正なサイズは通信障害と区別する。
- 成功した画像は同一フレーム内で保持し、失敗した画像だけを再取得する。20枚の一斉取得を4枚並列へ制限した。
- 全領域の取得が失敗し404/410を含む場合はカタログを1回更新し、同じ予報対象時刻のURLが変わった場合だけ取り直す。同じURLを延々と再試行しない。一部領域だけの404は、利用可能な画像を残して欠測とする。
- スライダー位置は即座に更新し、画像取得は120msで最後の選択へ集約する。以前の親状態の反映で新しい入力が取り消されないよう保護した。古い要求・先読みを中止し、選択した先読みは表示要求へ昇格する。
- 待機列を含む全体期限で基礎処理へ中止を伝える。キャンセル非対応のSDKでも、古い処理の終了を待って最新要求を止めたり、後続SDK呼出しを始めたりしない。再生は未完了フレームを積まない。
- 内部の取得失敗メッセージと「再試行」パネルを通常画面から除去した。最後に表示できた画像・日時・実況/予測ラベルを一致させ、タイムライン内に選択時刻の「取得中／更新待ち」を表示する。初回未取得・一部欠測は0mm/hと混同しない。お気に入りの保存失敗表示は維持する。
- 背景地図のOPFS、キャッシュキー・形式、SW本体は変更していない。既存キャッシュは削除しない。オフラインでも初回のfetchはSWキャッシュを利用でき、失敗時の通信反復は止める。

## 上限・ライフサイクル

| 項目 | 設定 |
|---|---|
| HTTP・本文・デコードの1試行 | 4秒 |
| 追加再試行 | 最大2回、待機400ms→1000ms |
| Retry-After | 待機時間に反映。4秒を超える指定は次の更新機会へ延期 |
| フレーム全体 | JMAは待機列・再試行・カタログ再解決を含め18秒。GSMaPは従来の25秒を維持し、待機列も含める |
| カタログ取得 | 最大14秒。同時取得は共有し、1利用者の中止で他の利用者を止めない |
| 並列数 | 2フレームまで、先読み1フレームまで、各フレーム4画像まで（合計最大8画像） |
| フレーム待機列 | 4件まで。通常の連続選択では古い要求を中止して最新のみ残す |
| 本文サイズ | 画像1枚512KiB、カタログ1MiB。stream読込中にも上限を検査 |
| 合成済みキャッシュ | 従来どおり両ソース合計10件・25MiB、表示中を保護 |

選択変更・ソース変更・背景化・pagehide・offlineで不要なフレーム処理を止める。共有カタログも待機中に非表示／オフラインになった場合、次の再試行HTTPを開始しない。上限まで失敗した場合は更新待ちとし、以後はオンライン復帰・画面復帰・定期更新・再選択を契機に回復する。無限に再試行する仕組みではない。

## 検証観点と確認結果

正常・異常・境界・状態遷移を先に整理した。単体テストは実関数を使い、応答順や待機は制御Promise/fake clockで固定。ブラウザ試験はWindowsのChromium / WebKit、実MapLibre・実SW・CacheStorageを使い、外部API境界だけを有効なPNG/JSON fixtureに置き換えた。ブラウザはworkers=1で順次実行した。

| 観点 | 結果 |
|---|---|
| 実況・+10分・+1時間・+6/+7時間・+10時間・+15時間 | 両ブラウザで日時・予測ラベルが実際の画像と一致 |
| 10時間先の20画像が初回503、その後正常 | 両ブラウザで40要求（20枚×2回）により操作し直さず回復 |
| 20画像のうち1枚だけ初回503 | 単体テストで合計21要求。正常な19枚を再取得せず、並列fetchは4以下 |
| 継続503 | 20枚×3回＝60要求で終了。内部エラー文なし。元の実況日時・降水量を保持し更新待ちへ移行 |
| 404の旧世代→新カタログ | 両ブラウザでカタログ更新1回、同じ予報対象時刻を新URLで表示 |
| 404でカタログが変わらない | 先読みから表示に昇格した経路も含め、単体テストで1回更新後に終了。旧画像を保持 |
| 連続選択 | App単体テストで8時刻の要求のうちプロバイダーが開始したのは最初と最後だけ。未完了の古いプロバイダーを待たず最後を表示 |
| 短い入力burst・遅い旧応答 | 両ブラウザで通過した未来画像の取得0。実行開始した古い時刻も4画像以下で停止し、新時刻の表示後に旧応答を解放しても上書きなし |
| 成功フレームの再選択 | 両ブラウザで10時間先の要求数40のまま増加せず、メモリキャッシュを再利用 |
| 雨雲のオフライン再起動 | 両ブラウザで保存済み20画像から10時間先を再表示。別用途のCacheStorage内のデータも維持 |
| timeout・429・本文上限・キャンセル | 単体テストで期限時の中止、Retry-After、サイズ超過拒否、待機中の中止、期限切れ待機ジョブの未実行を確認 |
| 初期欠測・お気に入り保存拒否 | 対象E2Eで欠測と0mm/hの区別、保存拒否時の入力とエラー表示の維持を確認 |

テスト作成中には、古い親状態の反映が新しい入力を取り消す競合を対象E2Eで検出し、実装修正と単体回帰テストを追加した。また、個別のPlaywrightキー送信では処理負荷により120ms以上空くため、burstの試験は同一タスク内のinputイベントに固定した。通常キー操作は予報境界ケース等で別に確認した。旧応答は時間待ちで推測せず、後から明示的に解放するfixtureとした。
