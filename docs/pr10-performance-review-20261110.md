# PR #10 本番性能問題の調査結果と改善案

調査日: 2026-11-10（JST）。利用者の報告環境: **iPhone 13 Pro Max、ホーム画面のPWA、主に標準地図（OSM）**。iOS版は未確認。

## 1. 結論

**PR #10には地図キャッシュ経路の重大な性能退行がある。前回の検証結果だけで、実用上問題なく完了したと判断することはできない。** 保存済みタイルを読むたびの全件探索、保存するたびの全件容量調査、保存キュー満杯時の取りこぼしを実装に対する再現ケースで確認した。起動・パン・ズームが広く遅くなり、保存警告が頻発するという報告と整合する。

本番のメインJavaScriptはPR #10のローカルビルドとbyte単位で一致した。Service Workerも改行コードを正規化すると一致した。[配信照合記録](../output/review-20261110-performance/production-check.json)。ただし、利用者のPWAが実際に制御されているWorker、端末内のOPFS内容、ストレージ容量、キャッシュヒット率は直接取得していない。端末の故障や容量不足とは断定しない。

今回行ったのは調査・再現・報告であり、製品コードの修正、PR作成、デプロイは行っていない。比較対象はPR #9後 `7102054` とPR #10後 `dda9efc`。

## 2. 確認観点と方法

| 観点 | 正常系 | 異常系 | 境界値 | 状態遷移 |
|---|---|---|---|---|
| 機能 | メモリ/OPFS/代替キャッシュのヒットと永続保存 | 一方のAPI停止時にも有効なデータを使う | 保存待ち32件と33件目以降 | 初回取得→保存→再参照 |
| 非機能 | タイル当たりのI/O量 | timeout後の残留作業、不要な全本文読込 | 1,200ファイル、600/400レスポンス | 連続パン・ズーム相当の複数要求→cancel |
| データ | 旧形式のキャッシュ再利用 | 有効ファイルがあるのにmiss扱い | 世代付きファイルと旧ファイル | PR前キャッシュ→PR後の読込 |
| UI | 表示継続と内部保存状態の区別 | 一時混雑を恒久保存失敗として表示 | 40要求中の8件保存見送り | memory-only→保存成功による表示の切替 |

実際のexport関数とSWスクリプトを呼び、ブラウザAPI境界に合成fixtureを置いた。キャッシュアルゴリズム自体はテストへコピーしていない。PR前のソースはGitから抽出し、同じfixtureで比較した。件数・本文byte・メタデータ読込回数はAPI呼出しを計測し、停止/timeoutは制御Promiseと仮想時計で固定した。

8ケースすべてが対象の問題を再現した。「8件成功」は不具合を再現する調査テストが成立した意味であり、製品が正常という判定ではない。60MB/40MB等はfixture内の本文読込要求量であり、実iPhoneの物理ディスク転送量・RAM使用量・実時間を測定した値ではない。

## 3. 指摘事項

### PERF-01 / P0（利用不能につながる重大問題）: キャッシュヒットにも全件探索が必要

対象: [opfsTileCache.ts:190](../src/lib/opfsTileCache.ts#L190)、[同:224](../src/lib/opfsTileCache.ts#L224)。PR #10で導入。

OPFSの世代付きファイルを探すため、1枚取得するたびに区分ディレクトリを最後まで列挙する。OPFSで読めても、その後に代替CacheStorageの全キーを列挙して比較する。ネットワーク要求の共有はその後なので、保存領域の探索自体は同時要求間で共有されない。

**再現P01:** 1,200枚を保存した状態でメモリを空にし、20枚の既存タイルを順に取得。

| 計測項目 | PR前 | PR後 |
|---|---:|---:|
| OPFSのファイル名列挙件数 | 0 | 24,000 |
| 目的ファイルのメタデータ読込 | 20 | 20 |
| 代替CacheStorageの全キー列挙回数 | 0 | 20 |
| ネットワーク取得 | 0 | 0 |

つまり「キャッシュにヒットしている」だけでは高速とはいえない。起動直後やメモリから追い出された範囲への移動で、保存量に比例した探索がタイルごとに発生する。

**改善:** 論理キー→現在世代/保存先/byte/取得日時の索引を持ち、通常読込を直接参照にする。旧形式の探索と索引復旧はまとめて1回、分割・中断可能に行う。OPFSと代替の新旧比較はメタデータで行い、必要な本文だけ読む。「OPFSを常に優先」として新版の代替コピーを無視する修正は避ける。

### PERF-02 / P0: 毎タイル保存時の全件整理がI/Oとキューを圧迫

対象: [opfsTileCache.ts:276](../src/lib/opfsTileCache.ts#L276)、[同:316](../src/lib/opfsTileCache.ts#L316)、[同:387](../src/lib/opfsTileCache.ts#L387)、[同:414](../src/lib/opfsTileCache.ts#L414)。PR #10で頻度・方式を変更。

- **P05:** 既存1,200枚に1枚追加。PR前はこの書込みでは整理を行わず、PR後は1,201個すべての`getFile()`を呼ぶ。PR前のOPFS整理は60回の保存ごとだったが、PR後は毎回となった。
- **P06:** 代替キャッシュ600枚×100,000byteに1枚追加。PR前は既存本文の読込0、PR後は600本文・合計60,000,000byteを読む。`Promise.all`で全件の`arrayBuffer()`を開始するため、読込の並列数も制限されない。
- 整理が保存キューの完了条件に含まれる。1枚の保存が遅くなると、後続タイルの保存がその後ろで待つ。

iOSで`createWritable()`が利用できない/失敗する場合は代替キャッシュ経路となり、P06の影響を受ける。利用者端末が実際にどちらを使ったかは未測定であり、端末名だけから断定しない。

**改善:** 保存時にサイズを既知メタデータへ加減算し、通常保存の経路から全件本文読込を取り除く。整理は閾値・間引き・idle時のまとめ処理にし、1回のI/O件数と時間に予算を設ける。容量制限自体は維持し、Quota時のみ限定した追加整理と再試行を行う。世代保護は維持したまま旧世代を計画的に回収する。

### PERF-03 / P1: SWも保存のたびに全レスポンス本文を読み直す

対象: [sw.js:24](../public/sw.js#L24)、[同:51](../public/sw.js#L51)。PR #10で導入。

**P08:** JMA runtimeを399枚×100,000byteで準備し1枚追加すると、PR前の本文読込0に対し、PR後は400枚・40,000,000byteを読み直す。SWの上限整理が毎回`arrayBuffer()`でサイズを計算するためである。

このSW処理は標準地図OSMそのものの保存経路ではない。雨量画像・HTML/JS等の処理が、地図キャッシュと同じ端末上で並行して動作し、ストレージ/CPU/メモリ負荷を増やす要因である。大きなJSを含むshellも同様の会計方式を使う。

**改善:** SWもメタデータに基づく容量会計へ変更し、毎保存で全本文を読まない。`respondWith`/`waitUntil`による応答と寿命の保護は維持する。

### PERF-04 / P1: 読めるキャッシュがtimeoutに巻き込まれ、取消後の作業も残る

対象: [opfsTileCache.ts:191](../src/lib/opfsTileCache.ts#L191)、[同:226](../src/lib/opfsTileCache.ts#L226)、[同:542](../src/lib/opfsTileCache.ts#L542)。全件探索追加で影響が増幅。永続読込へのsignal非伝播自体はPR前から存在する。

- **P02:** 正常なOPFSタイルを取得しても、代替CacheStorageの`keys()`が止まると返却が2,500ms待たされる。
- **P03:** 有効な旧タイルが存在しても、ディレクトリ探索が2,500msを超えるとそのOPFS読込全体が失敗扱いとなり、ネットワーク取得へ進む。探索を後から解放すると1,200件の列挙が続いた。Promiseの期限は処理自体を止めていない。
- **P04:** パン・ズームで要求をabortしても永続読込は未完了のまま残り、探索完了後にはキャッシュデータを返した。MapLibre側で捨てられる場合でも不要I/Oは既に発生する。

**改善:** 読込全体にsignalと要求世代を伝え、各探索・API待ちの前後で中断を確認する。全体期限でタイムアウトしても裏で全件処理が継続しない設計にする。正常なコピーを得ている場合に、別保存先の停止だけで表示を待たせない。新旧判定との両立にはPERF-01の索引が必要。

### PERF-05 / P1: 保存待ちの混雑を保存エラーと表示し、見送った保存も回復しない

対象: [opfsTileCache.ts:433](../src/lib/opfsTileCache.ts#L433)、[App.tsx:175](../src/App.tsx#L175)、[同:1445](../src/App.tsx#L1445)。PR #10で導入。

**P07:** 正常に書込み可能なOPFSを用意し、最初のcloseだけを一時保留して40枚の取得完了を同時発生させた。32件は保存待ちとなり、8件は保存を見送り`memory-only`を発行。実ストレージエラーは発生していない。保留を解放すると32件だけ永続化され、40枚を再参照しても保存は32件のままだった。

Appはタイル単位の`memory-only`をそのまま「地図データを端末に保存できません」に変換する。後続の1枚が成功すれば警告を消すため、全体状態として正確でなく、混雑と成功の交互発生で表示が出入りする。byte数条件による保存見送りも同じ通知になり、根本原因を区別できない。表示中の「再試行」は気象カタログと雨フレームの再取得であり、見送った地図タイルの保存再試行ではない。

**改善:** 利用者の今回の意向に従い、再生成可能な地図キャッシュの内部保存失敗は通常画面へ通知しない。お気に入り等の利用者データの保存失敗は引き続き通知する。内部診断では混雑による延期、未対応、Quota、timeout、実書込み失敗を区別する。キューには制限を残し、表示優先・同一キー集約・余裕ができた際の限定再保存で回復する。無制限キューへの変更はしない。

### PERF-06 / P2: 実際の保存先・ヒット率・待ち時間を現在の診断から把握できない

対象: [opfsTileCache.ts:253](../src/lib/opfsTileCache.ts#L253)、[同:532](../src/lib/opfsTileCache.ts#L532)、[diagnostics.ts](../src/lib/diagnostics.ts)。

メモリhitは記録する一方、永続hitの採用箇所には保存先・時間・探索件数の記録がない。memory-onlyも原因がなく、直近100イベントだけなので連続操作で重要な記録が流れる。現在の警告だけから「OPFSが使えない」「端末容量が不足」とは判断できない。

**改善:** 集計カウンターとしてメモリ/OPFS/代替/ネットワークのhit・miss、読込p50/p95、探索件数、整理I/O、保存待ち数、延期数と原因を取得する。内部診断は座標・URL・お気に入り名を含めない。通常UIに警告を増やす方法ではなく、開発者向けの取得方法を設ける。

## 4. 利用者の質問への回答

| 質問 | 確認結果 |
|---|---|
| 起動・スクロール・ピンチが遅いのはPR #10の影響か | **影響する性能退行を確認した。** 同じタイル取得関数がこれらすべてで呼ばれ、蓄積量に比例したI/Oが追加されている。実機症状の全時間をこの原因だけに帰属させる計測はまだない |
| 保存できないというエラーは本当か | **保存待ちの混雑だけでも表示されるため、文言どおりの保存障害とは限らない。** 一方、見送られた8件が永続化されない動作も実在する。内部処理として扱う方針へ変更すべき |
| OPFS読込は正常か | 有効ファイルを読める経路自体は動作するが、探索負荷・timeout・代替側待ちに問題がある。OPFSはサーバーのバックエンドではなく端末内のブラウザ保存領域。実iPhone内の正常性は未確認 |
| 読込済みデータをキャッシュとして使えているか | メモリhitと通常の永続hitは再利用される。ただし永続hitでも重く、探索timeout時は存在するタイルをmiss扱いにする。保存見送りと地形キー変更も再取得要因 |

地形タイルのキーは`aw3d_v2_...`から`aw3d_v3.2_rgb-v3_...`へ変わっているので、旧地形キャッシュは初回から再利用されない。標準地図のrasterキーは維持されている。この地形キー変更は更新直後の負荷増加要因にはなるが、継続的な全操作遅延の唯一の説明にはならない。

## 5. 前回検証で見逃した理由

前回の96件とE2E14件の成功は、データ保全・世代競合・エラー処理を中心とした結果だった。性能の正常性まで裏づける証拠にはなっていなかった。

- **テスト観点不足:** 多数の既存タイルを持つ端末で、通常のhit/保存が何件のI/Oを発生させるかを測っていなかった。小さいfixtureの容量境界確認だけでは全件走査の増大を検出できない。
- **データ条件不足:** 空のブラウザcontextや少数の合成タイルが中心で、PR前から蓄積したキャッシュ・世代コピー・連続操作による保存待ちを十分に再現していなかった。
- **実装問題:** byte制限と世代保護のために、通常操作へ全件走査・全本文読込を組み込んだ。安全性の追加で常用経路が重くなることを評価できていなかった。
- **E2E範囲不足:** 既存E2Eは外部OSM等をabortし、AW3D fixtureも取得失敗を返す。SWとお気に入り・雨量表示の状態遷移は確認できても、実際の背景地図タイル取得・蓄積・パン/ピンチ性能の受入にはなっていなかった。WindowsのWebKitランナー成功もiPhone PWAの性能を保証しない。

これらは利用者側の操作や端末のせいとする問題ではなく、前回の実装と検証の不足である。

## 6. 改善の優先順位と再検証条件

1. **最優先:** PERF-01/02の通常読込・保存から全件走査/全本文読込を外す。お気に入りの原子性・Undo・画像世代保護は維持する。
2. **同時対応:** PERF-03のSW容量会計、PERF-04の中断、PERF-05の表示と保存回復を修正する。表示を消すだけで性能改善済みとはしない。
3. **受入前:** PERF-06の計測を用意し、API境界テスト、実ブラウザのOPFS/代替試験、iPhone PWAで段階的に確認する。

再検証では、まず正常/異常/境界/状態遷移を分け、次を満たすことを確認する。

- 空キャッシュ、600/1,200枚の既存キャッシュ、旧形式と新世代混在で起動・連続パン・ズーム・同じ範囲へ戻る操作を比較する。取得・表示時刻、network数、各層hit、I/O数を記録する。
- 通常の20枚hitで24,000件探索を発生させず、1枚保存のために既存60MBの本文を読まないことを自動検証する。
- OPFS正常/未対応/遅延/Quotaと代替正常/遅延を分離する。有効コピーがあるときに別保存先の停止だけで2.5秒待たないことを確認する。
- 32/33/40件の保存バーストで表示を妨げず、キュー制限を守り、見送りが再保存または明示された内部方針で回復することを確認する。
- cancel・timeout後に全件列挙や全本文読込が継続しないこと、旧結果を採用しないことを確認する。
- 通常画面に地図キャッシュの内部保存警告が出ず、お気に入り保存失敗の通知は残ることを確認する。
- 実地図タイルをfixtureで正常応答させるブラウザ性能試験を追加し、実地図読込をabortしたE2Eを性能受入に使わない。同一実機のスクリプトは直列実行する。
- 利用者のiPhone 13 Pro Max PWAで、iOS版・通信条件・蓄積量を記録し、初回と再訪の表示時間、操作中のフレーム停止を測定する。実機の時間目標は取得した基準値と合わせて定義し、今回の合成計測値を実機目標へ転用しない。

今回のE2E実行範囲は**未実施**。今回の目的はPR前後のキャッシュ処理量と決定的な停止/取消挙動の特定であり、そのための8ケースと公開配信照合を実施した。既存E2E全件の再実行では上記の性能欠陥を検出できないため、合格の根拠として追加していない。iPhone実機には接続しておらず、実端末性能の最終確認は残る。

PR #10全体を安易に戻す案は推奨しない。旧SWの広範なcache削除やお気に入りのデータ欠落対策まで戻るため、キャッシュ性能に関係する経路を狙って修正する。
